Method: all five index.html files were diffed pairwise and function-by-function

Every function independently modified by more than one package was extracted
from all versions, compared in full, and hand-merged. Non-JS assets (PWA
files, docs, SQL) were compared by diff/hash and taken from whichever package
had them unmodified from baseline, or merged where more than one touched them.

A live fetch of https://github.com/projectvaultin/expenses_tracker was used to
sanity-check baseline assumptions (see "Baseline discrepancy" under Conflicts).

## Package 03 — Android Sync / Realtime / Account Switching
================================================================================
Android sync:
  - androidTxnToEntry() date-bug fix carried over unmodified: the previous
    `String(raw).split(' ')[0]` assumed Postgres's space-separated timestamp
    format; Supabase's JS client actually returns ISO-8601 with a 'T'
    separator, so the old code silently returned the entire timestamp instead
    of a plain date. Fixed by deriving the date from local calendar fields.
  - transaction_date / created_at / type / payment_app / payment_mode mapping
    unchanged from baseline elsewhere in this function — no other package
    touched it, verified via diff against baseline.

Realtime: subscribeAndroidRealtime() and subscribeDebtsRealtime() merged from
Package 03 (only package that touched them) with defense-in-depth staleness
guards: every inbound realtime event is checked against BOTH a generation
counter (_acctGeneration, bumped on every logout/account-switch) AND the
current username (CU) AND the row's own user_id, before being written to
local storage. Any one of those three going stale is sufficient to drop the
event.

Logout: doLogout() now calls teardownRealtimeSubscriptions() before clearing
session state (previously realtime channels kept running in the background
after logout). Also bumps _acctGeneration and clears the inactivity timer.
No other package touched doLogout(); adopted from Package 03 as-is.

Account switching / cross-account protection: verified end-to-end. The
protection is layered:
  1. teardownRealtimeSubscriptions() actively removes both channels on
     logout/account-deletion, before the next account can log in.
  2. Every realtime callback snapshots its own userId/username/generation at
     subscribe time and re-checks all three on every event.
  3. syncAndroidTransactions()/syncDebts() re-check `if(!CU)` both before and
     after their Supabase await (an account switch mid-request cannot cause
     data to be written under the wrong account).
  4. subscribeAndroidRealtime()/subscribeDebtsRealtime() are only called with
     the userId resolved for the CURRENTLY logged-in account, at the end of a
     sync that already re-validated CU.
Simulated scenario (User A: login → realtime → logout; User B: login; event
belonging to User A arrives): the event is rejected by the generation/
username check in the realtime handler, and even if it somehow reached the
write path, the `if(!CU)`/CU-mismatch guards in the sync functions would
still block it. No cross-account write path was found.

## Conflicts
================================================================================
1. doLogin() / doSignup() double-submit fix (B1/B7): Packages 01 and 04
   independently found and fixed the same two bugs with different
   implementations. RETAINED: Package 04's version (setBtnLoading()-based),
   because it's consistent with the shared loading-state helper used
   throughout the rest of the merged UI. Package 01's mobile-number duplicate
   check (absent from Package 04's doSignup) was ported into the retained
   version — this was a real fix that would have been silently dropped
   otherwise.

2. Forgot-password OTP (sendForgotOTP/verifyForgotOTP/resendOTP) — SECURITY
   REGRESSION CAUGHT: Package 04's UI rewrite of these functions reintroduced
   Package 01's user-enumeration bug ("No account found with that mobile
   number or email" — a message that reveals whether an account exists).
   Package 04 had clearly built its version from a pre-Package-01 baseline
   and never saw Package 01's fix. RETAINED: Package 01's enumeration-safe
   logic (always advance to the same OTP screen, generic messaging,
   indistinguishable timing) as the authoritative security layer, with
   Package 04's countdown-timer UI (initOtpCountdown/stopOtpCountdown,
   resend-cooldown-disabled state, setBtnLoading on submit) layered on top.

3. Login-2FA and forgot-password OTP validity window mismatch: Package 01's
   security-authoritative expiry is 10 minutes (LOGIN_2FA_OTP_TTL_MS /
   FP_OTP_TTL_MS); Package 04's visual countdown timer was hardcoded to 5
   minutes (OTP_EXPIRY_SECONDS=300) and independently disabled the UI at that
   point. RETAINED: the countdown now derives its displayed duration from the
   same 10-minute constant Package 01 uses for the actual expiry check, so
   the visible timer and the enforced expiry agree. (OTP_RESEND_COOLDOWN_SECONDS,
   a separate 30-second "you can request another code" cooldown, is unaffected
   and unchanged.)

4. syncAndroidTransactions() / syncDebts() — dual DOM writers: Package 03
   added `if(!CU)` cross-account guards, a realtime-health-monitor call, and
   wrote a detailed status string directly to #drawer-synccount /
   #drawer-debtsynccount. Package 04 independently rewrote the same two
   functions to route their status through beginSyncOp()/endSyncOp(), which
   itself writes to the SAME #drawer-synccount element via setCloudStatus().
   Merged naively, the two would have fought over that element on every sync
   (whichever wrote last would win, with no aggregation). RESOLVED: kept
   Package 03's `if(!CU)` guards (before AND after the Supabase await —
   cross-account safety), its subscribeAndroidRealtime()/subscribeDebtsRealtime()/
   startSyncHealthMonitor() calls, and its detailed status text — but routed
   that status text through endSyncOp()'s `detail` parameter instead of a
   second direct write, so setCloudStatus() remains the single writer of
   #drawer-synccount / #drawer-debtsynccount.

5. confirmDeleteAccount() / performDeleteAccount(): Package 03 added a
   teardownRealtimeSubscriptions() call to the (then confirm()/prompt()-based)
   account-deletion flow. Package 04 independently replaced the entire flow
   with a themed modal, splitting it into confirmDeleteAccount() (just opens
   the modal) and a new performDeleteAccount() (does the actual deletion) —
   and Package 04's performDeleteAccount() did not have Package 03's realtime
   teardown, since Package 04 branched before Package 03's fix existed.
   RESOLVED: kept Package 04's modal-based confirmDeleteAccount() unmodified,
   and merged Package 03's teardownRealtimeSubscriptions()/inactivity-timer-clear
   call into Package 04's performDeleteAccount() — otherwise a deleted account
   would have left its realtime channels running exactly like the doLogout()
   bug Package 03 fixed, just via a different code path.

6. Splice-introduced duplicates (self-caught, not a cross-package conflict):
   during automated assembly, performDeleteAccount(), findUserByIdentifierAsync(),
   and deliverOTPEmail() were each briefly inserted as duplicates because the
   assembly script initially treated them as exclusive to one package, when
   findUserByIdentifierAsync()/deliverOTPEmail() were actually already present,
   byte-identical to baseline, in Package 04. Caught by an automated
   duplicate-function-name scan before packaging; the redundant re-insertions
   were removed and the originals kept (or, for performDeleteAccount, the
   correct merged version was kept and Package 04's stale un-merged copy
   was removed).

7. Baseline discrepancy (flagged, not resolved): Packages 01 and 05 both
   state their baseline index.html was 5,180 lines. A live fetch of
   github.com/projectvaultin/expenses_tracker/index.html during this
   integration showed roughly 4,081 lines at the head of the file structure
   (partial view). This integration proceeded on the assumption that
   Packages 01/03/04/05's stated ~5,180-line baseline is the more recent
   and correct one (all four packages agree with each other on structure and
   line-count order of magnitude; only the live fetch disagreed, and a single
   partial fetch is weaker evidence than four independent packages'
   consistent diffs against each other). This is flagged for manual
   verification against the actual current main-branch commit before merging
   upstream — see Remaining Issues.

## Regressions
================================================================================
Detected and fixed during this integration:
  - Forgot-password user-enumeration regression (see Conflict 2) — fixed by
    retaining Package 01's logic instead of Package 04's.
  - OTP countdown/expiry duration mismatch (see Conflict 3) — fixed by
    deriving the countdown's displayed duration from the real TTL constants.
  - #drawer-debtsynccount and #drawer-realtime-status DOM elements were
    referenced by merged JS (from Package 03) but did not exist in the
    Package-04-based HTML — added the two missing <div> lines to the drawer
    markup (Package 03's original markup, verified byte-for-byte before
    insertion).
  - Three splice-introduced duplicate functions (see Duplicates) — caught by
    an automated post-assembly scan and removed before packaging.
  - Two documentation files referenced internal-only PACKAGE_0N_REPORT.txt
    audit artifacts that are not part of the shipped repository (one in
    README.md, one in a SQL comment, plus three more found on a follow-up
    sweep) — reworded to be self-contained.
  - Service worker cache name bumped v6 → v7, since index.html's content
    materially changed in this integration and the service worker's own
    header comment documents this as required practice ("Bump CACHE_NAME
    whenever the website's important static files change") — otherwise
    existing installs could stay pinned to a stale cached HTML shell after
    this deploy.

Pre-existing issues found but NOT introduced by this integration (verified
identical across all five source packages, including the closest-to-baseline
Package 05, so out of scope for this integration to silently fix):
  - Three duplicate DOM `id` attributes: `receipt-file`, `receipt-add-btn`,
    `profile-av-ph`.
  - `document.getElementById('theme-toggle-app')` — no element with this id
    exists anywhere in the markup (only `theme-toggle-lock` and
    `theme-toggle-auth` do). Non-fatal: the reference is guarded with
    `if(appBtn)` and no-ops harmlessly.
  - `document.getElementById("admin-msg-inp")` (used in sendAdminMessage()) —
    no element with this id exists in the static markup in any of the five
    packages. Not guarded with a null check; calling sendAdminMessage() would
    throw. Present identically in all five source packages' baselines, so
    this predates all five audits and is flagged for separate follow-up
    rather than fixed here (fixing it would require either adding the
    missing input element to the admin-message UI or confirming it's
    generated dynamically somewhere this integration didn't find).
